# Read-only receiving verification of selected correction reproduction

This is an implementation preparation, not an actual receiving check, scientific approval, numerical reproduction, release or restore certificate. It is separate from sealed reproduction v1, which remains unchanged. Preparation executes only invented/injected tests and reads exact source functions; it opens no real cohorts, proposal arrays, traces or scientific outcome files, and invokes no actual checker, generator, SVD, optimizer, fitter, MCMC, prediction or score.

`verify_restored_reproduction.py` is a new read-only receiving CLI. It never invokes the production execution/resume controller. It reopens an explicitly supplied complete selected pass and recompares its three existing evidence routes. Missing or unresolved evidence fails verification; it is not repaired or turned into new work.

## Input and call

Use the frozen environment's actual interpreter with all five numeric variables already one:

```sh

VECLIB_MAXIMUM_THREADS=1 NUMEXPR_NUM_THREADS=1 \

  --bindings /absolute/fresh_receiving_bindings.json \
  --bindings-sha256 ACTUAL_BINDINGS_FILE_BYTE_SHA \
  --output /absolute/NEW_EXTERNAL_RECEIVING_CHECK \
```

The callable is `receiving_core.verify_receiving(bindings_path, bindings_sha256, output, python, *, dependencies=None)`. The dependency seam exists for invented tests and is absent from the production CLI. Any injected top-level fixture receipt has `status=synthetic_receiving_verification_fixture_passed` and `test_only_dependency_injection=true`; production staging must reject it. The production status is `corrected_selected_reproduction_restored_read_only_verified` and its injection flag is false.

The caller supplies and pins a sealed `corrected_selected_reproduction_receiving_bindings` file. It contains explicit reproduction root/code/selection roles, the selection byte SHA, an explicit `passes/<nonce>.json` completed-pass path and byte SHA, exact v1 and receiving source pins, optional original/pilot/numerical resolution reviews, an explicit historical-to-receiving path map, and trusted complete immutable root/file inventories. `interface_contract.json` defines the exact carrier. The receiving/stage orchestrator must establish those inventories from the trusted transport/stage inventory or separately byte-pinned extracted source/baseline roles. The verifier cannot establish trust by inventing its own expected inventory from a received tree.

Each directory mapping destination must have an exact complete trusted file inventory. Each exact-file destination must be independently pinned or part of such a tree. The resolver forbids symlinks, parent traversal, conflicting aliases and inconsistent nested mappings. Every failed attempt, diagnostic log, referenced trace and orphan file stays bound. It verifies the whole immutable file set and hashes before and after the scientific comparisons. Historical strings and frozen documents remain unchanged; only I/O resolution is adapted. The explicit fresh output must be outside all immutable roots/files and this implementation directory, and must not already exist. Verification never resumes or removes a claim.
